LESSON 03 ／ 作るフェーズ

モックを作る ― 裏側を作らずに、画面を先に作って整える

～ 仕様書の画面一覧から見た目だけの画面を作り、崩れ → テイスト → 細部 の順にブラッシュアップする ～

  • Claude デスクトップアプリを使います
  • 成果物：app/ の中の HTML と style.css
  • 保存や計算の処理はまだ作りません
  • 保存の仕組みは使わず、ファイルを開くだけで見られます

この回の前に用意しておくもの

仕様書 docs/spec.md が入ったアプリのフォルダ ＋ Claude デスクトップアプリ

アプリのフォルダ（このページでは例として my-app）の中に、仕様書 docs/spec.md がある状態から始めます（作る順番 docs/tasks.md は、この回では Claude Code に読ませません）。 Claude デスクトップアプリでそのフォルダを開き、Claude Code に指示を出します（デスクトップアプリと Claude Code が何かは、「フォルダを開く」の節の用語欄にまとめてあります）。Claude Code は無料プランでは使えないため、Claude の有料プランのご契約が必要です。プランの種類と料金は変わることがあるので、最新は Claude の公式ページでご確認ください。 間に合わなかった方は、LIVE講義では講師の画面で流れを見て、あとからご自身のPCで同じ手順を追ってください。

01

モックとは

モック＝見た目だけを作った画面です。ボタンを押しても何も起きず、保存も計算もしません。画面に何をどこに置くかを、実物の画面で確かめるために作ります。 この回で作るのは、ブラウザで開ける HTML と CSS のファイルだけです。画面が先に固まっていれば、あとの作業はすべてその画面の上で確かめられます。

用語

モック
見た目だけを作った画面。動きや保存の仕組みは入っていません。
HTML
画面に「何を」置くかを書くファイル。見出し・入力欄・ボタン・一覧などの並びを決めます。ファイル名の最後が .html になります。
CSS
画面の「見た目」を書くファイル。色・文字の大きさ・余白・角の丸み・要素の配置を決めます。ファイル名の最後が .css になります。
JavaScript
画面に「動き」を付けるプログラム。ボタンを押したときの処理、入力の確認、データの送受信などを書きます。この回では使いません。
裏側の処理
保存・計算・データの読み書きのように、画面の裏で動く仕組み。この回では作りません。
ブラッシュアップ
一度できたものを、見て・直して、少しずつ良くしていく作業。
崩れ
文字のはみ出し・重なり・ずれ、幅を変えたときの折れなど、意図と違う見た目になっていること。
テイスト
見た目の方向性。色・文字・余白・角の丸みなど、画面全体に共通する印象のこと。

なぜ裏側より先に画面を作るのか

このゼミでは、アプリを 「見た目 → 動き → 裏側」の順に、1段ずつ足して作ります。最初に作るのが、見た目だけのモックです。

一言でいうと：画面は目で見て直せますが、裏側の処理は動かすまで合っているか分かりません。目で見て直せるほうを先に終わらせ、そのあとの処理は、できあがった画面の上で1つずつ確かめながら足していきます。

  • 目で見て確かめられます。画面は開けばその場で合っているか分かります。保存や計算は、動かしてみるまで合っているか分かりません。先に画面があれば、あとから足す処理を、すべてこの画面の上で「押した結果がどう出るか」として確かめられます
  • うまくいかないとき、原因を探す範囲が狭くなります。画面と処理を一度に作らせると、思ったとおりに動かないときに、画面の置き方が悪いのか、処理が悪いのかが分かりません。画面だけを先に仕上げておけば、そのあとに起きた不具合は、あとから足した処理を先に調べればよいことになります
  • 1回の指示が小さくなり、確認画面を読み切れます。Claude Code はファイルを書き換える前に、何をどこに書くかを確認画面に出します。画面と処理をまとめて頼むと確認画面の中身が長くなり、読まずに許可することになります。見た目だけなら、出てくるのは HTML と CSS だけなので、自分が決めた見出しや入力欄の名前が入っているかを目で追えます
  • 仕様書と実物のずれに、作り込む前に気づけます。実物の画面に並べてみると、足りない入力欄や、要らなかった項目が見つかります。画面に置く項目が変われば、保存する項目も変わります。処理まで作ったあとで気づくと、画面と処理の両方を直すことになります。画面だけの状態なら、直すのは画面の1か所で終わります
  • 見た目が好みかどうかは、使う本人にしか決められません。自分が毎日開きたくなる画面かどうかを、AI は判断できません。見た目をあとまわしにすると、処理ができあがったあとで画面を変えることになり、直すのをためらって、気に入らないまま使い続けることになります
  • 残りの作業が数えられます。画面が1枚ずつ手元にあると、このあとの作業を「この画面のこのボタンに処理を足す」という形で、1つずつ数えられます
ここで作る画面は、あとで動きや裏側の処理を足すときの土台として使います。作り直す前提の下書きではありません。だから、この回のうちに「自分が毎回使いたい画面」になるまで整えます。 処理を足す段階で、「1件も無いときの案内」や「処理中の表示」のように、いまは出しようのない表示が増えることはあります。増えるのは足りなかった表示で、この回で決めた配置と見た目をやり直すわけではありません。

自分のアプリの型で、読み替えるところ

このページの例は、記録型の「食費メモ」（画面2枚・一覧あり）です。変換型・相談型のアプリは、次のように読み替えてください。

記録型（入れて、ためて、見返す）。このページの例「食費メモ」変換型（入れたものを別の形にして返す）相談型（質問して、答えをもらう）
一覧に仮のデータを3件入れる入力欄に長めの仮の文章、結果の欄に短い文章（1行）と長い文章（400字ほど）を置くやり取りの欄に、自分の発言と AI の返事を交互に3往復置く
画面1の「保存」を押しても何も起きない「変換」「生成」を押しても、結果の欄は最初に置いた仮の文章のまま変わらない「送信」を押しても、やり取りは最初に並べたまま増えない
「修正」→ 画面2 →「キャンセル」で戻れる画面が2枚以上あるときだけ見る。1枚で完結するなら飛ばす同じ
一覧：1行ごとに区切り線、金額は右揃え結果の欄：読みやすい幅を保ち、長い文章でも行間を詰めないやり取り：自分の発言と AI の返事を、位置や背景の色で見分けられるようにする

表は横にスクロールできます

なぜ短い文章と長い文章の両方を置くのか：本物の AI の返事は長さが毎回違い、1行のときと数百字のときでは、欄の高さも折り返し方も変わります。片方だけだと、もう片方の見た目を確かめられません。

02

アプリのフォルダを開いて、権限モードを「手動」にする

仕様書 docs/spec.md が入っているアプリのフォルダ（このページでは my-app。名前はご自身で付けたもの）を、Claude デスクトップアプリで開きます。 作る順番 docs/tasks.md は、この回では Claude Code に読ませません。なぜ：docs/tasks.md は、保存や計算まで含めて何をどの順で作るかを並べたものです。読ませると、この回では作らないと決めた処理まで作り始めます。

仕様書の「使う技術」も、この回では使いません。docs/spec.md のうち、この回で見るのは「画面一覧と遷移」だけです。「使う技術」に Node.js や React などを書いてあっても、この回のモックは HTML と CSS だけで作ります。なぜ：この回で確かめたいのは画面の配置と見た目だけです。起動用のファイルや設定ファイルまで作らせると、ファイルが増えて、どれを開いて確かめればよいか分からなくなります。

返答の最後に「仕様書には React と書いてありますが、指示どおり HTML と CSS だけで作りました」のように断られることがありますが、それで正しい状態です。仕様書は直しません。仕様書に書いた技術は、あとで動きや裏側の処理を足すときに使います。HTML と CSS をそのまま使える構成ならファイルごと使い、別の構成を選んだ場合は、ここで決めた配置・文言・色・余白を、その構成の書き方に移して使います。

用語

Claude デスクトップアプリ
PC にインストールして使う Claude の公式アプリ。この中から Claude Code を呼び出します。
Claude Code
指示を出すと、PC のファイルを実際に作ったり書き換えたりしてくれるツール。画面に答えを表示するだけのチャットとは別のものです。
セッション
Claude Code との1つの会話のまとまり。「＋ 新規」で新しく始めます。
ワークスペース
Claude Code が作業する場所として開いたフォルダのこと。
docs／spec.md／tasks.md
docs は documents（文書）の略で、文書を入れるフォルダの名前。spec.md は作るものを決めた仕様書、tasks.md は作る順番の一覧です。docs/spec.md は「docs フォルダの中の spec.md」の意味です。
  1. 1

    Claude デスクトップアプリを起動し、画面左上の </>（Claude Code）を押す

    左の一覧の上にある 「＋ 新規」 を押します。なぜ：前の会話と混ざりません。仕様書を作ったときの会話は、もう読ませなくて大丈夫です。仕様書はファイルとして残っているので、Claude Code はそれを読めます。

  2. 2

    画面の下のフォルダ名のボタン → 「フォルダを開く…」→ my-app を選んで「開く」

    なぜ：ここで選んだフォルダだけが Claude Code の作業対象になります。別のフォルダのままだと、そちらにファイルができます。

  3. 3

    入力欄の近くに「ローカル」と my-app の2つが出ていれば開けています

    「ローカル」は「この PC の中で動かす」という意味です。「クラウド」や「SSH」のような別の表示になっている場合は、押して「ローカル」に切り替えます。なぜ：この PC の中のフォルダを扱うには、この PC の中で動かす設定になっている必要があります。

  4. 4

    「このワークスペースを信頼しますか？」と出たら、場所を見てから「ワークスペースを信頼」

    表示されたフォルダの場所が、ご自身の my-app であることを見てから押します。なぜ：この確認は「そのフォルダの中のファイルを Claude Code が読み書きしてよいか」を聞いています。知らないフォルダなら押さないでください。

権限モードを「手動」にする

入力欄の下に、いまの権限モードの名前が出ています。ここを押すとモードの一覧が出るので、「手動」 を選びます。2026年9月24日時点では、新しいセッションが「オート」か「編集を受け入れる」で始まることがあります（どちらになるかは人によって違います）。新しいセッションを開いたら、そのたびにここを見てください。

用語

権限モード
Claude Code がファイルの書き換えやコマンドの実行をする前に、確認を求めるかどうかの設定。「手動」は、まだ許可していない操作の前に確認画面が出る設定です（前に「常に許可」を選んだ操作は、確認なしで進むことがあります）。「オート」は、多くの操作を人への確認なしで進める設定です。ファイルの書き換えなどはそのまま進み、それ以外の操作には安全性の確認が入ります。危険と判断された操作は止められますが、そのたびに確認画面が出るとは限らず、安全性の確認もすべてを見分けられるわけではありません。「編集を受け入れる」は、ファイルの書き換えやフォルダの中のファイル操作の一部を確認なしで進める設定です。
コマンド
PC に文字で出す命令。Claude Code はファイルの書き換えのほかに、コマンドの実行も提案してきます。
「権限をバイパス」は、確認をすべて省く設定です（2026年9月24日時点では、設定で許可しない限り一覧に出てきません）。このゼミでは選びません。「オート」と「編集を受け入れる」も、ファイルの書き換えなどを確認なしで進めることがあるので、この回では選びません。

なぜ「手動」にするのか：この回は、Claude Code が実際にファイルを作る回です。「手動」なら、どのファイルに何を書こうとしているかを確認画面で見てから許可できます。「オート」や「編集を受け入れる」のままだと、頼んでいないファイルまで確認なしで作られたり書き換えられたりしても気づけません。

確認画面は、作るファイルの数だけ出ます。画面が3枚なら、HTML 3つと style.css で4回以上出ます。回数が多いのは異常ではありません。途中で「常に許可」を選ばないでください。なぜ：一度選ぶと、以後その種類の操作は確認なしで進みます。このあとに出てくる「頼んでいない作業の確認」も、出ないまま通ってしまいます。

モードの名前や並びは、アプリの更新や契約の種類で変わることがあります。ファイルを書き換える前に毎回たずねてくる設定を選んでください。説明文に「常に確認」「毎回確認」と書かれているものが該当します。

03

指示①：仕様書の画面一覧から、モックを作らせる

Claude Code に docs/spec.md を読ませ、その「画面一覧と遷移」のとおりに画面を作らせます。次の型をそのまま入力欄に貼って送ります。画面の数や名前は仕様書から読み取らせるので、書き換える箇所はありません。

仕様書に「画面一覧と遷移」という見出しが無い場合は、指示の1行目の「画面一覧と遷移」を、ご自身の仕様書で画面のことを書いた見出しの名前（「画面構成」など）に書き換えて送ります。 画面のことを書いた節そのものが無い場合は、先に「docs/spec.md に、画面ごとの名前・何をする画面か・置く要素（入力欄・ボタン・一覧など）・どのボタンを押すとどの画面へ移るかを『画面一覧と遷移』の見出しで足してください。ほかの項目は変えないでください」と頼み、確認画面で中身を見てから許可します。 なぜ：画面の数と置くものが決まっていないと、AI は推測で画面を作ります。できた画面が意図と違っていても、見比べる相手が無いので気づけません。 
docs/spec.md を読んでください。その「画面一覧と遷移」に従って、見た目だけの画面（モック）を作ってください。

■ 条件
- 保存・計算・データの読み書きなど、裏側の処理は作らないでください。ボタンを押しても何も起きなくて構いません
- ファイルは app フォルダの中に、画面1枚につき HTML を1つ（最初の画面は app/index.html、ほかは app/edit.html のように役割が分かる名前）と、見た目をまとめる app/style.css の1つだけ。JavaScript は使わないでください
- 見た目の指定（CSS）は app/style.css にだけ書いてください。HTML の中に直接書き込まないでください
- インターネットから読み込むもの（画像・アイコン・書体・部品の詰め合わせ）は使わないでください。画像が要る箇所は、枠と「画像」の文字だけで表してください
- 作るのは app/ の中のファイルだけ。docs/ の中のファイルは読むだけで、書き換えないでください。すでに同じ名前のファイルがある場合は上書きせず、中身を見せて確認を待ってください
- ブラウザでファイルを直接開けば表示できるようにしてください（サーバーは使わない）
- 仕様書の画面一覧に「〜を押すと〜へ」と書いてあるボタンは、その画面へ移るリンクにしてください。それ以外のボタン（一覧の「削除」など）は、押しても画面が切り替わったり読み込み直されたりしないようにしてください（入力欄の送信は起こさない）
- 見た目を確かめるための仮のデータを入れてください。一覧があるアプリは一覧に3件ほど。そのうち1件は、文字が長いもの（20文字以上）と桁の大きい数字にしてください。一覧が無いアプリは、入力欄に長めの仮の文章を、結果の欄に短い文章（1行）と長い文章（400字ほど）を置いてください。やり取りが並ぶアプリは、自分の発言と AI の返事を交互に3往復置いてください
- 仮のデータは架空のものにしてください。実在の人名・社名・メールアドレスは入れないでください
- 色や飾りはまだ付けないでください。要素の配置だけで構いません
- 作り終えたら、ブラウザでの開き方を1行で教えてください（ターミナルのコマンドではなく、Finder やエクスプローラーからの開き方で）

用語

app
application（アプリケーション）の略。画面や処理のファイルを入れるフォルダの名前で、この回で初めて作られます。app/index.html は「app フォルダの中の index.html」の意味です。
index.html
アプリを開いたとき最初に出る画面の HTML に付ける、決まりごとの名前。あとで公開したりサーバーで動かしたりするとき、アドレスにファイル名を書かなくても最初に開かれる名前として決まっています。いま揃えておくと、そのときに直さずに済みます。ほかの画面は edit.html のように役割が分かる半角英数字にします。
リンク
押すと別の画面へ移る文字やボタン。HTML だけで作れるので、JavaScript が無くても画面の移動はできます。
仮のデータ
見た目を確かめるために入れておく、架空の記録や文章。本物のデータが無いと、一覧の行や結果の欄がどう見えるか分かりません。
ターミナル
文字で命令（コマンド）を打ち込み、結果を文字で受け取る画面。この回では使いません。
サーバー
画面からの求めに応じてデータを返したり保存したりするプログラム。この回のモックは HTML と CSS だけなので、サーバーは要りません。

条件の1行ずつに理由があります

条件なぜ
裏側の処理は作らない作らせると、画面の確認より先に保存や計算の動作確認が始まり、崩れの確認が後回しになります。この回は画面だけを見ます
HTML は画面の数だけ・CSS は1つ・JavaScript は使わないファイルが増えると、どれを見ればよいか分からなくなります。JavaScript が入ると「押しても動かない」が崩れなのか未完成なのか判断できなくなります
見た目の指定は style.css にだけ書くHTML の中に書かれていると、あとで「style.css だけを変えて」と頼んでも見た目が変わらず、原因が分からないまま止まります
インターネットから読み込むものは使わない通信が無いときに表示されず、崩れなのか、読み込みに失敗しただけなのか分からなくなります
作るのは app/ の中だけ。docs/ は書き換えない仕様書を書き換えられても気づけません。決めたことの正本は docs/spec.md に残しておきます
ブラウザで直接開けるサーバーも Node.js も要りません。ダブルクリックだけで確かめられます
「〜を押すと〜へ」のボタンだけはリンクで動かす画面が2枚以上あるとき、行き来できないと2枚目の見た目を確かめに行けません
それ以外のボタンは、押しても画面が切り替わらないHTML の入力欄のまとまりは、ボタンを押すと内容を送って画面を読み込み直す動きが最初から付いています。止めておかないと「押したら画面が変わった」が崩れなのか未完成なのか分からなくなります
仮のデータを入れる。長い文字・大きい桁・長い文章も混ぜる欄が空だと、行の見た目・区切り・文字の揃え方が確かめられません。全部が短いデータだと、どの行も1行に収まって当たり前に見えます。本物の記録には長いメモが混じり、AI の返事は数百字になることもあるので、先に混ぜておくと、幅を変える前から崩れが見つかります
仮のデータは架空のものこのあと画面のスクリーンショットを撮って AI に貼ったり、提出したりします。実在の名前は、そのまま人の目に触れます
色や飾りはまだ付けない色が付くと目が色に行き、要素のずれや文字のはみ出しを見落とします。さらに、テイストでは色と一緒に余白・幅・行間も動くので、配置と色を同時に変えると、どちらの指示で何が変わったのかが分からなくなります。先に配置だけを見て固めます
開き方を聞く（Finder やエクスプローラーからの開き方で）作ったファイルを自分で開けないと、確かめようがありません。この回はターミナルを使わないので、コマンドで答えられると、どこに打てばよいかで止まります

表は横にスクロールできます

画面の数と名前は仕様書に合わせて作られます。画面が3枚なら HTML も3つです。ファイル名は index.html 以外は自由ですが、小文字の半角英数字とハイフン（アンダースコアも可）だけにします。なぜ：日本語やスペースが入った名前は、開発の道具の一部で扱いが難しくなります。日本語の名前が付いていたら、「ファイル名を半角英数字に変えてください」と頼みます。

送ると、Claude Code は docs/spec.md を読み、ファイルを1つずつ作ります。「手動」なので、ファイルごとに「書き込みを許可しますか？」の確認画面が出ます。ファイルの場所が my-app/app/ の中であることと、中身に、自分が仕様書で決めた見出しや入力欄の名前（「今月の合計」「金額」など）が日本語で出てくることを見てから「一度だけ許可」を押します（確認画面の実物は 指示②・指示③ の節にあります）。作ったファイルを Claude Code が自分で点検するために、ファイルの一覧を出すコマンド（ls で始まるもの）や、ファイルの中身を探すコマンド（grep や find で始まるもの）の許可を求めてくることがあります。どれもファイルを読むだけで書き換えないので、許可して構いません。app フォルダを作るコマンド（mkdir app）が出ることもあります。これも頼んだ作業の一部なので許可します。

アプリの中のブラウザ欄だけで判断しないでください。Claude デスクトップアプリには画面を表示する欄がありますが、直後は前の状態のままだったり、この例のように style.css が読み込まれていなかったりします。最終の確認は必ずご自身のブラウザで開いて行います（次の節）。

04

ブラウザで開いて、崩れていないかを見る

開き方：Finder（Windows はエクスプローラー）で my-app → app → index.html をダブルクリックします。ブラウザが立ち上がり、モックが表示されます。

用語

ブラウザ
Safari や Chrome など、Web ページを見るソフト。HTML ファイルをそのまま開けます。
Node.js
JavaScript をブラウザの外（PC の上）で動かすための土台のソフト。サーバーを作るときなどに使います。この回では使いません。HTML と CSS だけの画面は、Node.js もサーバーも無しでブラウザが表示できます。

なぜサーバー無しで開けるのか：ブラウザは HTML ファイルを直接読んで画面にします。保存や計算の処理が無い今の状態では、ファイルを開くだけで十分です。あとで裏側の処理を足すときに初めて、サーバーが要るかどうかを考えます。

  • ダブルクリックで別のソフト（エディタなど）が開いた場合は、ファイルを右クリック → 「このアプリケーションで開く」（Windows は「プログラムから開く」）→ ブラウザを選びます。ブラウザの窓にファイルをドラッグしても開けます。なぜ：ダブルクリックでどのソフトが開くかは PC の設定で決まっていて、HTML ファイルにエディタが割り当てられていることがあります
  • 画面1の「修正」を押して画面2に移り、「キャンセル」で戻れるかを見ます。仕様書に「押すと〜へ」と書いたボタン以外（画面1の「保存」、一覧の「削除」など）は、押しても何も起きないのが正しい状態です。画面2の「保存」は、仕様書で「保存を押すと画面1へ戻る」と決めてあるので、リンクとして画面1に戻るだけで、内容は保存されません。この段階では、リンクで作られた「保存」（青い文字）と、ボタンで作られた「保存」（枠つき）で見た目が違って見えることがあります。色や飾りがまだ無いためで、崩れではありません。テイストを当てると揃います

崩れを見る5つの点

1つずつ、画面を見ながら確かめます。

仕様書の要素が全部あるか
見方docs/spec.md の「画面一覧と遷移」を横に開き、画面ごとに置くものを1つずつ指で追います
なぜ抜けは、あとで裏側の処理を足すときに「入れる場所が無い」という形で出てきます。余分な要素は AI が足したものです。仕様書に「作らない」と書いた機能のボタンが混じっていないかも見ます
文字がはみ出していないか・重なっていないか
見方見出し・入力欄の名前・一覧の文字を見ます
なぜはみ出しは、文字が長くなる本物のデータで悪化します
幅を変えても崩れないか
見方ブラウザの窓の右端をつかんで、縮められるところまで狭くし（スマホの幅は横 400px 前後）、そこから最大まで広げて、両端で見ます。一覧のいちばん右の列（「修正」「削除」など）が画面の外に出ていないかも見ます
なぜ自分ひとりで使うものでも、窓を小さくしたまま開いたり、スマホや大きい画面で開いたりします。列が多い一覧は、幅が足りなくなると右端から画面の外へ押し出され、押せないボタンがあることに気づけません
画面の移動が動くか
見方画面が2枚以上あるときだけ見ます。例：「修正」→ 画面2 → 「キャンセル」→ 画面1
なぜ移動できないと、2枚目の見た目を確かめに行けません。1枚で完結するアプリは、この点は飛ばして構いません
仮のデータが表示されているか
見方一覧があるアプリは一覧に3件。結果の欄があるアプリは短い文章と長い文章。やり取りが並ぶアプリは3往復
なぜ空だと行の見た目が確かめられません。長い文章を置いておかないと、欄の高さが足りるかが分かりません

折り返しそのものは、崩れではありません。幅に合わせて文章が複数行になっても、読めて、内容が欠けず、押す場所が見えていれば問題ありません。直すのは、文字の重なり・内容の欠け・1〜2文字ずつの不自然な折り返し・ボタンの見切れです。

崩れがあったら、その場で直させる

直したい箇所を1つ決め、次の型で送ります。スクリーンショットを撮って、入力欄に貼ります。Mac は ⌃⇧⌘4（コントロールも一緒に押す）で範囲を選んで撮ると画像がクリップボードに入るので、入力欄で ⌘V を押すと貼れます。⇧⌘4 で撮った場合はデスクトップに画像ファイルができるので、そのファイルを入力欄にドラッグします。Windows は Windows＋Shift＋S で撮って Ctrl+V で貼ります。貼る前に、名前・メールアドレス・業務の実データなど、外に出せないものが写っていないかを見ます。写っていたら、範囲を絞って撮り直します。なぜ：貼った画像は AI のサービスに送られます。

画面1の一覧で、メモ欄が狭すぎて文字が1〜2文字ずつ折り返されています（スクショを添付）。
メモ欄の幅を広げて、2行までに収まるようにしてください。
変更は app/style.css だけ。HTML と文言は変えないでください。文字を小さくしたり、内容を隠したりして逃げないでください。ほかは触らないでください。

なぜスクショを貼るのか：崩れを言葉にすると、どこがどう崩れているかが伝わりません。「一覧が変」では AI は別の場所を直します。画面そのものを見せれば、どの要素の話かが一致します。

ブラッシュアップは「崩れ → テイスト → 細部」の順に進めます。ここではまだ色や飾りは直しません。 順番を逆にして先に細部を直すと、テイストを変えたときに全体の余白や色が動き、直した細部がやり直しになります。
崩れが無くなったら、ここで画面ごとに1枚ずつスクリーンショットを撮っておいてください。ブラッシュアップの「前」の画面として、この回の提出物になります。テイストを当てると style.css の中身はほぼ全部が書き換わるので、撮るのはこのタイミングしかありません。

05

指示②：テイストを決める

テイスト＝見た目の方向性です。色・文字の大きさ・余白・角の丸みをまとめて指します。配置が崩れていない状態になったら、テイストを言葉で伝えて、style.css だけを書き換えさせます。

用語

テイスト
見た目の方向性。色・文字・余白・角の丸みなど、画面全体に共通する印象のことです。
アクセントカラー
画面の中で強調に使う色。白地に1色だけ使うと、ボタンや合計金額に目が行きます。
px
ピクセル。画面上の大きさの単位。文字の大きさを 16px のように指定します。
余白
要素と要素のあいだ、画面の端と内容のあいだの空き。狭いと詰まって読みにくくなります。

方向性を決める6つ

ご自身のアプリに合わせて言葉にします。決められないときは、下の例（落ち着いた色・白地・緑1色）をそのまま使って構いません。

全体の色
例落ち着いた色。地は白、アクセントは緑系を1色だけ
なぜ言葉にするのか決めないと AI が色を何色も使い、画面ごとに印象が変わります
文字
例本文は 16px 以上、見出しは太く、行間は広め
なぜ言葉にするのか小さい文字は読み飛ばしの元です。数字で言えば揃います
余白
例要素の間隔を広めに。左右にも余白を取り、内容は中央に寄せる
なぜ言葉にするのか余白の指定が無いと、要素が左上に寄った詰まった画面になります
ボタンと入力欄
例少し丸く。いちばん押してほしいボタン（例：「保存」）だけを色で強く見せ、それ以外は枠だけにする。「削除」のように取り消せない操作は、いちばん弱い見た目にする
なぜ言葉にするのか押せる場所が分からないと迷います。取り消せない操作が目立つと、押すつもりのなかったときに押してしまいます。強いボタンが画面に2つ以上あると、どれも強く見えなくなります
読みやすさ
例文字と背景、入力欄やボタンの枠と背景を、はっきり見分けられる濃さにする。色を敷いたボタンの文字は、地の色と強く差を付ける
なぜ言葉にするのか指定しないと、AI は薄い灰色の細い枠を置くことが多いです。作った直後の自分の画面では読めても、明るい場所や目が疲れているときに、どこに入力すればよいか分からなくなります
並ぶところ
例一覧があるアプリ：1行ごとに薄い区切り線。金額は右揃え／結果の欄があるアプリ：読みやすい幅を保ち、長い文章でも行間を詰めない／やり取りが並ぶアプリ：自分の発言と AI の返事を、位置や背景の色で見分けられるようにする
なぜ言葉にするのか数字は右で揃えると桁が比べられます。長い文章は幅が広すぎると目で追えません。誰の発言か分からないと読み返せません
言葉で決められないときは、好きな見た目を見せます。ご自身が普段使っていて見やすいと思うアプリやサイトの画面を1枚スクリーンショットで撮り、下の指示②に貼って、「■ 方向性」の代わりに次の一文を添えます。 「色の組み合わせと余白の取り方だけ、この画面の雰囲気に寄せてください。文字の内容・要素の並び・ロゴは真似しないでください。」 なぜ「色と余白だけ」と書くのか：そう書かないと、見出しの文言やボタンの並びまで似せてきます。仕様書で決めた画面とずれるうえ、人の作ったものをそのまま写すことにもなります。貼る前に、名前やデータが写っていないかを見てください。

テイストを当てる指示の型

指示①と同じセッションで、続けて送ります。指示①と違い、この型はご自身のアプリに合わせて書き換えます。（　）の中が書き換える箇所です。「並ぶところ」は、上の表からご自身のアプリに当てはまるものを1つ選んで書きます（例：読書の記録なら「1行ごとに薄い区切り線。読み終えた日は右揃え」）。

app の見た目の方向性（テイスト）を整えてください。裏側の処理は引き続き作らないでください。

■ 方向性
- 全体：（落ち着いた色。地は白、アクセントは緑系を1色だけ）
- 文字：（本文は 16px 以上、見出しは太く。行間は広め）
- 余白：（要素どうしの間隔を広めに。画面の左右にも余白を取り、内容は中央に寄せる）
- ボタンと入力欄：（少し丸く。いちばん押してほしいボタンだけを色で強く見せ、それ以外は枠だけ。「削除」のように取り消せない操作は、いちばん弱い見た目に）
- 読みやすさ：（文字と背景、入力欄やボタンの枠と背景は、はっきり見分けられる濃さに。背景とほとんど同じ濃さの薄い灰色の枠は使わない。色を敷いたボタンの文字は、地の色とはっきり差を付ける）
- 並ぶところ：（1行ごとに薄い区切り線。金額は右揃え）

■ 条件
- 書き換える前に、いまの app/style.css を app/style-before.css という名前でコピーして残してください
- 変更は app/style.css だけ。HTML の構造（要素の並びや文言）は変えないでください
- CSS だけでは方向性のとおりにできない箇所があれば、HTML は変えずに、どこが・なぜできないかを教えてください
- すべての画面に同じテイストを当ててください
- 窓の幅を狭くしても、一覧の文字が1〜2文字ずつ折り返されたり、右端のボタンが画面の外に出たりしないようにしてください

なぜ先にコピーを残すのか：テイストを当てると style.css の中身はほぼ全部が書き換わります。当てたあとで「前のほうが良かった」と思ったとき、コピーがあれば「app/style-before.css の中身で app/style.css を上書きしてください」と頼むだけで確実に戻せます。ブラウザは index.html が読み込んでいる style.css だけを使うので、コピーを置いても見た目は変わりません。

なぜ style.css だけを変えさせるのか：HTML を変えると、前の節で確かめた配置がまた変わり、崩れの確認をやり直すことになります。見た目は CSS だけで変えられるので、HTML には触らせません。

送ると style.css の書き込みの確認画面が出ます。場所が my-app/app/style.css であること、中身が色や文字の指定であることを見てから「一度だけ許可」を押します。

頼んでいない作業は断ってください。この例では、style.css を書いたあとに Claude Code が、英語で Create preview copies with inlined CSS（プレビュー用のコピーを作る）と書かれたコマンドの実行を求めてきました。指示に無い作業なので 「拒否」 を押しています。拒否しても、頼んだ style.css の変更はそのまま残ります。 なぜ断るのか：頼んでいないファイルが増えると、どれが本物か分からなくなります。何をするコマンドか読んで分からないものは、通しません。 このほか、Claude Code が自分で見た目を確かめようとして、ブラウザを起動するコマンド（Google Chrome を含む長い1行や、--screenshot を含むもの）の許可を求めてくることもあります。これも頼んでいないので「拒否」で構いません。見た目はご自身のブラウザで確かめます。拒否すると返答に「ブラウザでの表示は確認できていません」と書かれることがありますが、style.css の変更は残っています。

ブラウザで開き直して見る

開いたままのブラウザは、再読み込みすると新しい見た目になります（Mac は ⌘R、Windows は F5）。なぜ：ブラウザは前に読んだファイルを表示し続けています。読み直させないと、直したはずなのに変わらないように見えます。

テイストを当てたら、「崩れを見る5つの点」をもう一度通します。余白や文字が大きくなると、列どうしの幅の取り合いが変わります。テイストの前は読めていた一覧が、当てたあとで1〜2文字ずつ折り返されたり、右端のボタンが画面の外に出たりすることがあります。あわせて、画面から少し離れて、入力欄の枠が見えるか、ボタンの文字が地の色に溶けていないかも見ます。見つけたら、崩れを直す指示の型で app/style.css だけを直させます。

06

指示③：細部を1つずつ直す

テイストが決まったら、気になるところを 1回の指示で1点だけ 直していきます。

なぜ1点ずつなのか：まとめて頼むと、どの指示でどこが変わったか分からなくなります。気に入らない変更だけを戻したいとき、1点ずつなら「さっきの1点を戻して」で済みます。

細部の例：ボタンの位置と目立たせ方／文字の大きさ／一覧の列の幅／余白の広さ／区切り線の濃さ。文言や要素の並びを変えたいときは HTML も直すことになるので、そのむねを指示に書きます（下の「HTML を変えないとできないと言われたら」の型を使います）。

細かい所を1つずつ直します。次の1点だけ直してください。ほかは触らないでください。
変更は app/style.css だけ。HTML は変えないでください（HTML を変えないと直せない場合は、直す前に教えてください）。

- （「保存」ボタンを入力欄の右下に寄せて、ほかのボタンより目立つ色にする（画面1・画面2の両方））

「ほかは触らないでください」を毎回入れる理由：この一言が無いと、AI は頼んだ1点のついでに周りも整え始めます。整えた結果が良くても、何が変わったか把握できなくなります。上の例は位置と色の2つを書いていますが、どちらも「保存を目立たせる」という1つの目的なのでまとめています。目的が別のものは、別の指示に分けます。

HTML を変えないとできないと言われたら

合計を枠で囲んで目立たせる、複数の要素を1つの箱にまとめる、といった変更は、囲むための入れ物が HTML に無いとできません。そのときだけ、範囲を絞って HTML を触らせます。

さきほど「HTML を変えないとできない」と言われた（　　　）を直してください。

■ 条件
- 変えてよいのは、囲むための入れ物の要素を足すことだけ。文言・要素の順番・入力欄やボタンの数は変えないでください
- 変える前に、どのファイルのどこに何を足すかを教えてください

なぜ「入れ物を足すだけ」と書くのか：範囲を書かずに「HTML を直してよい」と言うと、AI は画面全体を作り直して返してくることがあります。入れ物を1つ足すだけなら、確かめた配置はそのまま残ります。

指示③のあとに、頼んだ1点のほかの提案（ファイルの整理、コピーの作成など）が付いてくることがあります。頼んでいないものは「拒否」を押します。拒否しても、頼んだ1点の変更はそのまま残ります。

直したら、ブラウザを再読み込みして見ます。気になる点が残っていれば、また1点だけ頼みます。言葉にしにくい細部は、スクショに印を付けて貼ります（Mac の「プレビュー」、Windows の「Snipping Tool」（以前の「切り取り＆スケッチ」）で丸や矢印を描けます。アプリの名前は更新で変わることがあります）。

直した1点と、その理由は、そのつどメモに書き残します。この回の提出物になります。

メモの書き方（例）

1点につき「何を」と「なぜ」が書いてあれば十分です。1行で構いません。

  • 一覧のメモ欄が1〜2文字ずつ折り返されていたので、メモ欄の幅を広げた。窓を狭くしても読めるようにしたかったから
  • テイストの緑が見出しとボタンの両方に付いて、どこを押すのか分かりにくかったので、見出しは黒に戻した。押せる場所だけに色を使いたかったから
  • AI が「並べ替え」のボタンを足していたので消した。仕様書の「やらないこと」に入れていたから

07

見直して、仕様書と揃える

ブラッシュアップを終えたら、次の4つを見ます。

  1. 1

    「崩れを見る5つの点」をもう一度通す

    細部を直したあとで幅を変えたら折れる、はよく起きます。

  2. 2

    仕様書の画面一覧と、実物の画面を見比べる

    ブラッシュアップの途中で、要素の名前や並びが変わっている場合があります。まず Claude Code に「docs/spec.md の画面一覧と遷移と、いまの app/ の画面で違うところを一覧にしてください。まだ何も変えないでください」と頼み、出てきた違いを1つずつ、画面を仕様書に戻すか、自分が採用した変更として仕様書を直すかを決めます。決めていない変更は、画面を仕様書に戻します。採用した変更だけ「docs/spec.md の画面一覧と遷移の〜を、〜に直してください。ほかの項目は変えないでください」と頼みます。なぜ：仕様書と画面が食い違ったままだと、あとで裏側の処理を足すとき、AI がどちらを正としてよいか分からなくなります。AI が勝手に変えた画面を仕様にしてしまうと、決めた「やること」「やらないこと」がずれます。

  3. 3

    裏側の処理は作っていないことを確かめる

    正しい状態は、アプリの型によって違います。

    • 記録型：画面1の「保存」を押しても一覧に記録が増えない。ブラウザを閉じて開き直しても増えていない（画面2の「保存」「キャンセル」は、リンクとして画面1に戻るだけです）
    • 変換型：「変換」「生成」を押しても、結果の欄は最初に置いた仮の文章のまま変わらない
    • 相談型：「送信」を押しても、やり取りは最初に並べたまま増えない

    なぜ「何も起きない」が正しいのか：この回で作ったのは画面だけで、保存の処理も、AI を呼ぶ処理も入っていません。押して何かが起きたら、Claude Code が頼んでいない処理を足しています。「JavaScript や保存の処理は入れないでください。入っていたら外して、作ったファイルの一覧を教えてください」と頼みます。

  4. 4

    docs/tasks.md に終わった印を付ける

    作る順番 docs/tasks.md を作ってある方は、いまの画面でできたと言えるタスクを - [x]（終わった印）に変えておきます。「画面が1枚出る」のほかに、「修正画面へ移動して戻る」のように、画面の移動だけで確かめられるタスクも終わっています。保存や計算を含むタスクは、まだ終わっていません。なぜ：印が実物とずれていると、次に作り始めるときに、できているものをもう一度作らせることになります。

ここで作った画面は、あとで動きや裏側の処理を足すときの土台になります。モックは捨てるものではありません。 だから、この回の時点で「自分が毎回使いたい画面」になっているかを見ておいてください。

この回で作るもの

終わったとき、手元に次の4つがある状態にします。この回の課題の内容は commmune のゼミスレッドでご案内し、提出は「ゼミ参加者向け 事前課題提出受付フォーム」から開催3日前までにお願いします（Home の「ゼミのルール・修了要件」）。演習サイト Boarding Pass の理解度チェックもあります。

用語

commmune
DMM 生成AI CAMP の受講生向けコミュニティサイト。ゼミごとのスレッドで課題や連絡を案内します。

app/ の中の HTML と style.css

前と後のスクリーンショット

ブラッシュアップ前（色を付ける前）と後の画面を、画面ごとに1枚ずつ。アプリのフォルダの中に shots フォルダを作って入れておくと迷いません（例：shots/before-index.png）。何がどう変わったかを見せるためのものです。

自分の判断で直した点のメモ

断った場面のスクリーンショット（あれば）

頼んでいない作業の確認画面が出て断った場面があれば、そのスクリーンショット。出なかった場合は不要です。

Pitfalls

よくあるつまずきと対処

詰まったら、Home の「分からないことが出てきたらこの順番で」の順（スクショを撮って AI に聞く → ゼミ掲示板）で進めてください。

ブラウザで開いても色が付かない・素の状態で出る

style.css が読み込まれていません。

対処：style.css が index.html と同じ app フォルダにあるか見ます。無ければ「app/style.css が読み込まれていません。直してください」と頼みます。アプリの中のプレビュー欄で見ている場合は、ご自身のブラウザで開き直してください。

ダブルクリックでブラウザ以外のソフトが開く

エディタで中身の文字が出ます。

対処：右クリック → 「このアプリケーションで開く」（Windows は「プログラムから開く」）→ ブラウザ。または、ブラウザの窓にファイルをドラッグします。

指示のたびに画面の構成が変わる

崩れの確認をやり直しになります。

対処：「HTML の構造は変えない」「ほかは触らない」を毎回入れます。

Claude Code が JavaScript や保存の処理を作り始めた

ボタンが動き、裏側ができてしまいます。

対処：確認画面で「拒否」。指示に「裏側の処理は作らない」「JavaScript は使わない」を戻します。

頼んでいないコマンドの許可を求められた

何をするか分からないまま通してしまいます。

対処：内容を読みます。頼んでいない・分からないなら「拒否」。頼んだ作業の結果は残っています。

何を直したいか言葉にできない

指示が曖昧で、別の場所が直ります。

対処：スクショに丸や矢印を付けて貼ります。

細部を先に直して、テイストで全部変わった

直した細部がやり直しになります。

対処：「崩れ → テイスト → 細部」の順に戻ります。今回は1回分のやり直しで済みます。

直したのにブラウザが変わらない

前の表示のままです。

対処：再読み込み（⌘R／F5）します。

ファイル名が index.html・edit.html でない

このページの例と違って不安になります。

対処：例なので、ご自身の画面に合わせた名前で構いません。最初の画面だけ index.html にします。

権限モードが「手動」になっていない

確認なしでファイルが書き換わります。

対処：入力欄の下のモード名を押して「手動」に。名前が違うときは、ファイルを書き換える前に毎回たずねてくる設定（説明文に「常に確認」「毎回確認」とあるもの）を選びます。

画面が仕様書と違うものになった

あとで裏側を足すとき、どちらが正か分からなくなります。

対処：画面を直すか、仕様書を直すかをご自身で決めて、両方を揃えます。

仕様書に「画面一覧と遷移」の見出しが無い・名前が違う

AI が画面の節を見つけられず、推測で画面を作ります。

対処：指示①の1行目を、ご自身の仕様書の見出しの名前に書き換えます。画面の節が無ければ、先に画面の節を足させてから指示①に進みます（「指示①：仕様書の画面一覧から、モックを作らせる」の節の注意書き）。

仕様書 docs/spec.md が手元に無い

読ませるものが無く、最初の指示が送れません。

対処：先に「目的／やること／やらないこと／画面ごとの名前と置く要素」を箇条書きで書き出し、Claude Code に「これを docs/spec.md にまとめてください」と頼んでから、指示①へ進みます。

仕様書の「使う技術」に書いた部品の一式を作り始めた

HTML と CSS 以外のファイル（設定ファイルや起動用のファイル）が増えます。

対処：確認画面で「拒否」。「この回で作るのは app/ の中の HTML と CSS だけです。ほかのファイルは作らないでください」と送り直します。

確認画面が何度も出て、「常に許可」を押した

以後、確認なしでファイルが書き換わり、頼んでいない変更に気づけなくなります。

対処：入力欄の下のモード名を押して「手動」になっているかを見ます。そのうえで「これまでに作った・書き換えたファイルの一覧を教えてください」と頼み、app/ の外にファイルが増えていないかを見ます。

「style.css だけを変えて」と頼んでも見た目が変わらない

見た目の指定が HTML の中に直接書かれています。

対処：「HTML の中に書かれている見た目の指定を、すべて app/style.css に移してください。見た目は変えないでください」と頼みます。

テイストを当てたら、前のほうが良かった

どこをどう戻せばよいか分かりません。

対処：「app/style-before.css の中身で app/style.css を上書きしてください。ほかは触らないでください」と頼みます。テイストを当て直すより確実に戻ります。

テイストを当てたら、狭い幅で一覧が崩れた

余白や文字が大きくなり、列の幅が足りなくなっています。

対処：崩れを直す指示の型で、スクショを貼って app/style.css だけを直させます。

ブラッシュアップ前のスクリーンショットを撮り忘れた

提出する「前」の画面がありません。

対処：app/style-before.css が残っていれば、app フォルダを丸ごとコピーし、コピーした側の style.css を style-before.css の中身に置き換えて開くと、前の画面を撮れます。残っていなければ、撮り直そうとせず、提出時に「前を撮り忘れた」と書いてください。なぜ：色を外す指示を出すと、いま整っている画面が崩れて、そこからやり直しになります。

途中で利用の上限に達して、指示が通らなくなった

ブラッシュアップの途中で止まります。

対処：ここまでに作ったファイルはそのまま残っています。使える量が戻ったら、同じフォルダを開き直して続きから頼みます。上限の量と戻る周期は契約の種類で違い、変わることがあるので、最新は Claude の公式ページでご確認ください。

Windows で、Git が必要だと言われる

2026年9月24日時点のアプリは、Git という道具が無くても作業を始められます。Git が要るのは、Git を使う「ワークツリー」という設定をセッションでオンにしたときです（このゼミでは使いません）。古い版のアプリは、Windows では Git が無いと始められませんでした。

対処：まずアプリを最新版にし、「ワークツリー」をオフにします。それでも出るときは Git for Windows を入れてから、Claude デスクトップアプリを一度終了して開き直します。表示される文言や必要なものは更新で変わることがあるので、画面の案内に従ってください。

Claude デスクトップアプリが入っていない／有料プランが未契約

フォルダを開くところから先に進めません。

対処：LIVE講義では講師の画面で流れを見て、あとからご自身のPCで同じ手順を追ってください。導入で詰まったら、スクショを撮って AI に聞く → ゼミ掲示板の順で。
